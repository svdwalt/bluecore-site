NetSecAgent: letting Claude operate the lab firewalls and ISE, and what it cost

24 Nov 2026 · 12 min read

Our earlier posts measured how far the Cisco ISE API reaches. The next question was the obvious one: if nearly everything is reachable through an API, can a language model do the work, instead of a person writing curl commands?

We built an agent to find out, called NetSecAgent. You type a request in plain English, such as "why can this PC not reach that server" or "block DNS to 8.8.8.8 from the PC behind the second firewall and prove it". The agent does the work on the devices and reports what it changed and how it checked.

Everything below was measured in the BlueCore lab between 13 and 20 November 2026. The devices were a Cisco Secure Firewall Management Center 10.0.1 managing three FTD 10.0.0 firewalls, a FortiFirewall 7.0.15, and Cisco ISE 3.5 patch 4. It is a lab tool, and a later section says what would have to change before it goes near a production network.

The short answer

It works better than we expected for diagnosis, and well enough for changes that we now use it instead of the web interfaces for most lab work. The cost is small: 22 sessions came to 12.66 US dollars in API use, with a median of about 0.20 per session and 4.55 for the most expensive one.

Three things made the difference, and none of them is the model:

  1. One thin REST tool per product, not a function per feature.
  2. A notes file that holds only calls we had run on the real device.
  3. A fixed ending to every answer: what was changed, what was verified, and what is left.

It is not autonomous. One integration step had no API at all, and the one long task we gave it needed a person twice and about an hour of that person's time.

How it is built

The agent is a loop from the Claude Agent SDK running Claude Opus 5.5, behind a small web page. Every tool call passes two hooks first: one writes it to an audit log, the other decides whether it may run.

We chose Opus because the work is long chains of tool calls where one wrong step changes a firewall, and we wanted the most capable model for that. We have not tested a cheaper model on the same requests. At a median of 20 cents a session, cost has not yet given us a reason to.

A thin tool and a notes file

The FMC tool takes a method, a path, a body and parameters, and nothing else. There is no "create rule" function and no "add NAT" function, so the model builds each request itself.

What it builds them from is a notes file. The file holds read calls, request bodies and procedures that we ran against this FMC, each with the date. Next to it sits a list of all 779 API paths, taken from the FMC's own API description. The model searches that list when it needs a path the notes do not cover.

Here is one entry as the agent reads it, with the client address replaced and the last sentence shortened:

## Verified: why is this traffic allowed or blocked (packet tracer)

POST /api/fmc_troubleshoot/v1/domain/{domainUUID}/packettracer/traces with

{"device": {"id": "<dev>", "type": "Device", "name": "ftd1"},
 "interface": {"id": "<physical interface id>", "type": "PhysicalInterface", "name": "inside"},
 "protocol": "TCP", "sourceIPType": "IPv4", "sourceIPValue": "<client address>", "sourcePort": "40000",
 "destinationIPType": "IPv4", "destinationIPValue": "8.8.8.8", "destinationPort": "23"}

`device` needs id, type and name (a bare id answers "Device value is missing"). The answer (HTTP 202) is
deviceResponse[0].phases[], each with type, result (ALLOW or DROP), config (the matching access-list line
with the rule name and rule-id) and additionalInformation. Measured: Telnet from ftd1's client is DROP in an
ACCESS-LIST phase naming lab-ftd-policy. It is a simulation: nothing is sent, so use it freely. This is your
main evidence for "why is X blocked".

The file's header says when it was run: "Everything under Verified was run against fmc-lab on 2026-11-17." Each entry gives the method, the path, a body that worked, the mistake that fails, and what the answer looks like. That is all the integration there is.

This kept the tool at 175 lines. Supporting a new FMC feature means adding a paragraph of notes, not code. The rule for the notes is strict: only what was measured. While we built the lab, guessed request bodies were the main source of failed runs.

The tool handles what the model should not think about

  • Login. The tool gets the token, keeps it, and logs in again once if a call answers 401.
  • TLS. The FMC's certificate is self-signed, so the tool trusts that exact certificate and no other. Without it the tool refuses to send the login.
  • Lockout. A rejected login means the password is wrong. The tool then refuses every later call to that device until it is restarted, so the agent cannot lock an account by retrying. We learned that lesson the hard way on ISE, as the API coverage post describes.
  • Size. Large replies are cut with a note, so one long list cannot fill the model's context.

Evidence, not opinion

The agent is told to prove what it says. On a firewall that means packet tracer, which names the exact rule that dropped a flow, then hit counters, then a real test from the client PC. Asked why a client could not use Telnet while web browsing worked, it answered with this, from the firewall:

Phase: 4  Type: ACCESS-LIST  Result: DROP
access-list CSM_FW_ACL_ advanced deny tcp ifc inside any ifc outside any object-group TELNET rule-id 268434436
access-list CSM_FW_ACL_ remark rule-id 268434436: L4 RULE: lab-deny-telnet
Drop-reason: (acl-drop) Flow is denied by configured rule

It then showed which rule the web traffic matched instead. That run made eight tool calls in 28 seconds and cost 0.28 US dollars.

The long task: pxGrid between ISE and the FMC

The hardest request was to connect the FMC to ISE over pxGrid, so that the firewalls learn users and security group tags from ISE. It took 92 tool calls over 35 minutes. Ten of the eleven failed tool calls in the whole data set happened here.

What the agent did by itself:

  • Enabled the pxGrid service on the ISE node and checked the port answered.
  • Worked out which CA chains the FMC had to trust by asking the ISE ports directly with OpenSSL.
  • Created the FMC's key and certificate request, and loaded the certificates into the FMC.
  • Tested the client certificate against ISE before touching the FMC, by registering a throw-away pxGrid client and then deleting it.
  • Read the ISE pxGrid log to find out why its first certificate was rejected.

Where it needed a person:

  • Its first certificate was self-signed, and ISE rejected it. The agent found the reason in the log (Validation error: self signed certificate) and tried twice more, once with the CA flag set, before it stopped. The certificate had to be signed by a CA that ISE trusts, which meant our lab CA and a person.
  • The FMC has no API call for its ISE connection form. The agent prepared every value and handed over a table. A person typed it in.
  • DNS. The FMC's connection test then failed on name resolution, twice, for two different reasons. The second one was a DNS server answering with a lifetime of zero, which the FMC resolves once and then reports as "Host not found". That was found with a packet capture and a person, not by the agent.

Counting both sides: the agent's session cost 4.55 US dollars and ran for 35 minutes. Getting from there to a passing connection test took about another hour of a person's time, most of it on the DNS problem. That hour is our estimate from file timestamps, not a stopwatch. For a first run of this integration, with no notes to start from, we think that is a fair price, but the API bill is the smaller part of it.

The result is a runbook written for an agent, with every call tested, which the next run can follow without the false start. That is the pattern we expect to keep: the first run of a new kind of task is slow and supervised, and what it leaves behind is the notes that make the second run cheap.

What stops it doing damage

ControlWhat it does

Audit logEvery tool call and the start of its result, with passwords and tokens removed
Cost caps8 US dollars per request and 40 per day
Fixed reportEvery answer ends with Changed, Verified and Notes

The one refused request was a test. We asked the agent to shut down a virtual machine that belongs to a different lab. It answered that the address was not part of the firewall lab, changed nothing, sent no traffic to it, and said who should do it instead. That cost 0.02 US dollars.

The guard is a deny-list that matches text, and the model has a free shell, so it catches only the obvious. It is not a security boundary, and we do not treat it as one.

The agent was also careful in ways we did not write rules for. When a curl command failed certificate verification against the FMC, it wrote: "I'm not going to turn verification off", and went back to the tool that had the pinned certificate.

One note on the model itself, because firewall work is dual-use: the API account the agent runs on has Anthropic's access for defensive security work, and in these 22 sessions the model declined nothing on safety grounds. We ran no comparison on an account without that access, so we cannot say how much it mattered.

What does not work yet

  • Long waits. A deployment that takes minutes is a poor fit for a chat page. We interrupted two runs while they were waiting, and each time the agent reported honestly that it had started the deployment and had not confirmed the result.
  • Tasks that span products and people. pxGrid needed a CA, a DNS server and a web form. The agent did its part and handed over cleanly, but a person still had to hold the whole picture.
  • First attempts at something new. Without notes for a task, the agent guesses like anyone else. The self-signed certificate was a reasonable guess and a wrong one.
  • The guard. A deny-list is acceptable in a lab and nowhere else.

Before this goes near production

  1. Approval for writes. The lab agent changes configuration without asking. On a real network, a change and its deployment should be proposed, approved by a person, and only then run.
  2. Read-only accounts for read tasks. Most of the useful requests were questions. They need a read-only role, not the administrator.
  3. An allow-list in place of the guard. Named operations with fixed shapes, not a free REST call and a free shell.
  4. One API user per integration. On the FMC, a second login with the same user ends the first one's token.
  5. Notes per software version. FMC paths differ between versions. Take the path list from the customer's own FMC.

What we would tell someone starting out

  1. Build one generic tool per product and put the knowledge in a notes file that people can read and review.
  2. Write down only what you have run. A guessed request body costs more than a missing one.
  3. Make the agent prove its answer with the device's own evidence, and make every answer end the same way.
  4. Put the lockout latch and the audit log in before anything else. Both are small and neither depends on the model.
  5. Expect the first run of a new task to need you. Keep what it learned, so the second run does not.
